Extraction Approach

DecisionChosen?Which pipeline / what has to be built
Reuse existing pipelinenoNo toolkit pipeline reads Python/Odoo: pipelines/ has outsystems, java-angular, node-express-react only, and none of their layout assumptions (OML/XML, Java/TS source trees) fit an Odoo addon tree.
Build new pipelineyesA small pipelines/odoo/ extractor in this project: Python ast over models/, wizard/, report/*.py → models, fields (type, required, relation, compute/depends, selection values), _inherit/_inherits, _sql_constraints, @api.constrains, action_* methods; XML over views/ → views per model, menus, actions; security/ → ACL matrix (model × group × CRUD) and ir.rule domains; __manifest__.py → dependency graph. Output JSON into analysis/odoo/knowledge-base/. Validated against hand-built ground truth for 5 models (res.partner, product.template, sale.order, sale.order.line, stock.picking) per qa-loop-goal-pattern.md.

Reasoning: Odoo is unusually extractor-friendly — models, fields, relations, security and menus are all declarative, so a few hundred lines of Python cover the structure. What it cannot extract is method *behaviour* (what action_confirm does); that is read per method at Stage 1/2 for the in-scope flows only. ~300 models × ~20 fields each is far beyond a reliable hand read.

Who chose it, and when: the user, Stage 0 gate in chat, 2026-10-14 (recorded in PROJECT.md).
